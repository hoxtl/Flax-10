\section{System Overview}

StudyFlax is a web-based time management application built for students and teaching staff at King's College London. King's College London students typically manage their timetable, assignment deadlines, task lists, and society activities across several separate tools, and keeping track of all of them at once is difficult. The platform brings all of that into a single interface. Teaching staff can also use it to create and manage modules, set deadlines, and publish reading lists, which students then see directly within their own dashboard.

The system is split into two independently deployed parts: a React frontend served via Vite, and a Django backend connected to a PostgreSQL database. The two sides communicate only through a RESTful HTTP API, so neither is coupled to the other's implementation. The backend also connects to several external services: the King's College London timetabling system for importing student schedules, OpenAI for the AI study coach, Mapbox for the campus map, and the Transport for London API for public transport routing. The development environment is containerised using Nix Flakes and Docker Compose, which kept the setup consistent across the whole team.

\section{Architectural Pattern}

The system follows a three-tier architecture, separating the user interface, application logic, and data storage into distinct layers (Figure~\ref{fig:architecture}). A decoupled approach, in which the frontend and backend are independently deployed and communicate only through a REST API, was preferred over server-side rendering with Django templates. The application requires a high degree of interactivity: the calendar supports drag-and-drop rescheduling and live event resizing, the dashboard widgets update independently of one another, the study timer runs continuously in the background, and several views maintain complex local state across user interactions. Rendering these interfaces through server-generated templates would require a full round-trip to the server for every meaningful user action, which is neither fast enough nor architecturally practical for this kind of feature set. A dedicated React SPA handles its own state and re-renders incrementally without involving the server, while the Django backend focuses entirely on business logic and data persistence.

The presentation tier is the React SPA running in the user's browser. It has no direct access to the database and holds no session state shared with the backend. All data is fetched and submitted through HTTP requests to the REST API, and the application re-renders based on the responses it receives.

The application tier is a Django REST Framework server responsible for all business logic. It exposes a single API namespace at \texttt{/api/}, with endpoints organised by feature area, for example \texttt{/api/events/}, \texttt{/api/tasks/}, and \texttt{/api/societies/}. Authentication is handled per request: each request carries a token in the \texttt{Authorization} header, which the server validates using DRF's \texttt{TokenAuthentication} class. No session state is held server-side, keeping the application tier fully stateless.

The data tier is a PostgreSQL database accessed exclusively through Django's ORM. No raw SQL is used anywhere in the codebase. In development, user-uploaded files such as profile photos are written to disk and served through a configured media root.

External services (OpenAI, Mapbox, and the TfL API) are called from the application tier only, never from the frontend. This ensures that API keys remain server-side and that the backend can validate and transform external responses before returning them to the client.

\section{Frontend Design}
\label{sect:frontend}

The frontend is built using React with Vite as the build tool, and follows a component-based architecture. The application is structured around a set of page-level components and over 180 smaller reusable components, organised by feature domain (e.g.\ \texttt{calendar/}, \texttt{tasks/}, \texttt{societies/}).

Routing is handled by React Router, with all authenticated pages wrapped in a shared \texttt{DashboardLayout} component that provides the navigation bar and global UI shell. This ensures consistent layout and navigation behaviour across the application without duplicating structure in each page.

State management follows two patterns depending on complexity. Simple, localised state is handled with React's built-in \texttt{useState} and \texttt{useEffect} hooks. For more complex, cross-component state, the application uses React Context combined with a reducer pattern. The most notable example is \texttt{CalendarContext}, which manages event data, modal visibility, and selected date state across the entire calendar feature using a dedicated reducer for predictability. Nine context providers are used in total, covering areas such as theming, 
notifications, task completion, and timer state.

API communication is abstracted into a dedicated \texttt{api/} service layer, keeping data-fetching logic separate from component rendering logic. Custom hooks (e.g.\ \texttt{useCalendarEvents}, \texttt{useTimerLogic}) further encapsulate reusable behaviour and are consumed by page components.

Styling uses a combination of CSS Modules and styled-components, with all colour values defined in a central \texttt{variables.css} file. This is described further in Section~\ref{sect:design-decisions}.

\section{Backend Design}
\label{sect:backend}

The backend is a single Django project (\texttt{Flax10}) with one application (\texttt{studyFlax}). All models, serialisers, views, and business logic sit within this app, with each feature domain organised into its own subdirectory.

\subsection{API Layer}

All API endpoints are registered under \texttt{/api/} and routed through a single URL configuration at \texttt{studyFlax/urls/api\_urls.py}. Most endpoints use plain function-based views with \texttt{@api\_view} decorators, which kept things simple for endpoints that do not need the full CRUD pattern. Two DRF \texttt{ViewSet}s are registered via a \texttt{DefaultRouter}, specifically for study session history and calendar sharing, where the router-generated routes were a better fit.

The API covers the following functional domains: authentication, user profiles and settings, calendar events and timetable import, modules and deadlines, tasks and task lists, study timer sessions, group work projects, societies, notifications, analytics, and admin tools.

\subsection{Models}

Models are split into domain subdirectories under \texttt{studyFlax/models/}: \texttt{auth/}, \texttt{calendar/}, \texttt{modules/}, \texttt{tasks/}, \texttt{timer/}, \texttt{society/}, \texttt{groupwork/}, \texttt{social/}, and \texttt{notifications/}. The \texttt{User} model extends Django's \texttt{AbstractUser}, with added role fields (\texttt{student}, \texttt{teacher}, \texttt{pending\_teacher}), profile fields such as photo, bio, and home address with geocoordinates, and a linked \texttt{UserSettings} model for per-user preferences including theme, daily study targets, and sleep schedule. The custom user model was defined before any initial migrations were run, which was important because retrofitting it afterwards would have required a full database reset.

\subsection{Serialisers}

Each model domain has a corresponding serialiser module under \texttt{studyFlax/serialisers/}. DRF \texttt{ModelSerializer} is used throughout. Where the API response needs to differ from the raw model fields, custom \texttt{validate\_*} methods or \texttt{Serializer\allowbreak{}MethodField}s are added, for example to resolve nested relationships or compute derived values such as reading time estimates.

\subsection{Signals}

Django signals handle side effects that should not be mixed into view logic. When a group work suggestion is responded to, or a society announcement is published, a signal handler creates the relevant \texttt{Notification} record automatically. Notifications are therefore created reliably regardless of what triggered the change.

\subsection{Authentication}

Registration creates a \texttt{User} record and returns a DRF auth token in the same response. Login validates credentials and returns the existing token. Logout deletes the token server-side so it is immediately invalidated. Password reset uses a time-limited token stored in the \texttt{ResetPasswordToken} model, with the reset link sent by email through Django's SMTP backend.

\subsection{Admin}

The backend exposes a set of admin-only API endpoints under \texttt{/api/admin/}, restricted to users with the \texttt{staff} role. These allow administrators to manage user accounts, oversee registered societies, and access platform-wide analytics without going through Django's built-in \texttt{/admin/} panel. Django's default \texttt{/admin/} interface is also available for direct database-level inspection and management during development. Role-based access is enforced at the view level using a custom permission check against the \texttt{is\_staff} flag on the \texttt{User} model.

\subsection*{Frontend Design Analysis}

\textbf{High Cohesion:} \\
The frontend demonstrates high cohesion through a careful separation of responsibilities
across its architectural layers, as illustrated in Figure~\ref{fig:component_frontend}.
Each module encapsulates a single, well-defined concern within the system: page-level
components are responsible only for UI composition, shared state is centralised within
dedicated contexts such as \texttt{CalendarContext} and \texttt{AuthState}, and
domain-specific custom hooks encapsulate reusable behaviour independently of UI
components. As a concrete example, \texttt{useCalendarEvents} encapsulates all calendar
data-fetching behaviour and exposes it to \texttt{StudentPages} without those pages
requiring any knowledge of the underlying API calls or state management implementation.
This organised approach is consistently applied across all feature areas including
calendar, tasks, timer, and notifications, ensuring that related logic and presentation
are grouped together within their respective modules. Each layer therefore has a
well-defined purpose, improving readability, maintainability, and testability across the
codebase.

\vspace{0.5cm}

\textbf{Low Coupling:} \\
The frontend enforces low coupling through the implementation of clear interaction
boundaries between components and layers. Communication between modules occurs through
well-defined interfaces: props for UI components, context providers for shared state, and
service abstractions within the \texttt{APILayer} for backend communication. By extracting
domain logic into custom hooks and delegating data access to service modules, components
avoid direct dependencies on the implementation details of other parts of the system. For
example, page components depend on context and hooks rather than directly invoking API
calls, reducing tight coupling between the UI and data-fetching logic. The
\texttt{HttpClient} serves as the single point of communication between the frontend and
the Django backend, ensuring that changes to the backend interface require updates only
within the \texttt{APILayer} rather than propagating throughout the component tree. This
separation ensures that changes within a given module have minimal impact on other modules,
provided that external interfaces remain stable, reinforcing modularity, scalability, and
ease of refactoring across the frontend codebase.

\subsection*{Backend Design Analysis}

\textbf{High Cohesion:} \\
The backend also observes high cohesion by grouping related responsibilities in clearly defined layers and feature-oriented subpackages, which can be seen in Figure~\ref{fig:component_backend}. Within the \texttt{studyFlax} application, domain
models are organised under specific subdirectories such as \texttt{auth},
\texttt{calendar}, \texttt{modules}, \texttt{tasks}, \texttt{society}, \texttt{timer},
\texttt{notifications}, and \texttt{groupwork}, whereas additional concerns such as
serialisers, views, URLs, signals, and utilities are stored and maintained in their own dedicated modules. As a result, each backend file or package serves one principal purpose: persisting domain state, validating API data, transforming API data, handling request logic, or wiring routes. To provide an example, the \texttt{SignalHandlers} layer is exclusively responsible for event-driven side effects such as creating notifications when a society announcement is published or a group work suggestion is replied to, keeping the logic separate from view and serialiser code. This organisation supports high cohesion
because code that changes for the same reason is kept together, making the backend easier
to navigate and extend without blurring the responsibilities of individual
components.

\vspace{0.5cm}

\textbf{Low Coupling:} \\
The backend enforces low coupling by mediating interactions between parts of the system through interfaces, instead of having tightly coupled implementations. This is visible in the structure of Figure~\ref{fig:component_backend}. URL configuration
delegates incoming requests to specific view modules; these views then rely on serialisers and the ORM for validation and persistence, whereas additional concerns such as creating notifications, handling emails and external service communications are extracted into dedicated signals and service modules, avoiding duplication across request handlers.
As an example, the \texttt{ORM} layer serves as the single point of database access for both
the \texttt{Serialisers} and \texttt{Services} layers independently, meaning neither
layer is aware of the other's existence or implementation. Moreover, the feature-based
package structure reduces unnecessary cross-domain dependencies, since calendar logic,
task logic, society logic, and authentication logic are each strongly encapsulated within their own backend areas. This ensures that modifications within one domain have minimal impact on other parts of the system, provided that external interfaces remain unchanged. Such a structural approach encourages separation of concerns, maintainability, and ease of independent testing across the backend codebase.

Unlike the prior SEG project, in this project API is handled using \texttt{Django REST Framework} and practicing JSON-based API call formatting. In deployment such method functions in a however less intuitive way-- A static, manifest-based api pipeline instead of an inter-server communication. This differs from what is practiced under development environement, which is a localhost server based frontend-backend 2 servers paradigm. This actually creates sort of difference on how api pathing and http call handling behaves upon deployment, forming challenges to deploying attempts and our transport-layer knowledge base for debugging unexpected http behaviors(unexpected errors like 401, 502, 400, 404, etc.).

While Django-Vite helps backend processing asset manifestations, Whitenoise enables django to serve static file upon requested.
\section{Key Design Decisions}
\label{sect:design-decisions}

This section documents the significant design decisions made during development, focusing on choices where alternatives were considered or where the approach was non-obvious.

\subsection{Custom User Model with Unified Role System}

A custom user model was defined from the outset of the project, extending Django's \texttt{AbstractUser} to incorporate roles (\texttt{student}, \texttt{teacher}, and \texttt{staff}) and profile-specific fields such as profile photo and home address, with study preferences such as year and major stored in a linked \texttt{UserSettings} model. This decision was made early and deliberately, as retrofitting a custom user model after initial migrations would have required resetting the database entirely. The unified model ensures that role-based behaviour, such as restricting module creation to teachers and administration tools to admins, is handled consistently through a single identity model rather than through separate profile tables.

\subsection{Token-Based Authentication}

Token-based authentication was chosen over session-based authentication to keep the backend stateless. No session data is stored on the server, and each request is authenticated independently via a token passed in the \texttt{Authorization} header. This fits the decoupled SPA and API architecture naturally, as the React frontend and Django REST Framework backend share no server-side state.

DRF's built-in token model was preferred over JSON Web Tokens (JWT), which is a common alternative for single-page applications. JWT is stateless by design: once issued, a token cannot be invalidated without additional infrastructure such as a server-side denylist or a short-expiry and refresh-token cycle. DRF tokens, by contrast, are stored in the database and are deleted immediately when a user logs out, providing instant and unconditional invalidation. For a student-facing application where users may share devices, reliable session termination on logout was considered more important than the marginal infrastructure simplicity that JWT statelessness provides.

\subsection{Course-Prefix Mapping for Module Onboarding}

During onboarding, modules are automatically assigned to a student based on their selected major using a course-prefix mapping (e.g.\ selecting Computer Science maps to all modules with the prefix \texttt{6CCS} or \texttt{5CCS}). The alternative of manual per-user module assignment was rejected as it would not scale and would place an unnecessary burden on both users and administrators. The prefix-mapping approach means that as new modules are added to the system, they are automatically surfaced to the correct students without any additional configuration.

\subsection{CSS Variables for Theming}

Colour values are primarily defined as CSS custom properties in a central \texttt{variables.css} file, which underpins the light and dark theme toggle and enforces visual consistency across the UI.


\subsection{Tasks as a Standalone Page}

The task management feature was designed to function as a central point of integration across the application: tasks can be linked to calendar events, completed through study timer sessions, and associated with module deadlines. Supporting these relationships requires the tasks view to offer dedicated navigation, filtering by module or deadline, and persistent interaction state. A floating overlay panel does not provide the space or the navigational context these integrations require, and embedding cross-feature links within an overlay would create a confusing interaction model where one part of the interface triggers actions in another. Implementing tasks as a dedicated standalone page gives the feature the same structural status as the calendar, modules, and other core sections of the application, and makes it possible to build the full set of cross-feature interactions without imposing constraints on any surrounding page.

\subsection{Navigation: Top Bar and Bottom Bar}

The navigation system needed to provide persistent access to all major sections of the application without affecting the layout of page content. A collapsible sidebar does not satisfy this requirement: toggling it changes the width available to the main content area, which repositions elements on pages with dense or precisely laid-out content such as the calendar, the Bento dashboard, and the campus map. A permanently open sidebar resolves the layout-shift problem but consumes a significant portion of the viewport on smaller screens, where horizontal space is already limited.

A persistent top navigation bar on desktop and a fixed bottom navigation bar on mobile address both constraints. Neither bar occupies any horizontal space used by page content, so layouts remain stable regardless of navigation state. The bottom bar on mobile follows the established platform convention for primary navigation and places the most frequently used sections within thumb reach. This combination gives users constant access to navigation while ensuring that page content is never displaced.


\subsection{Modular Bento Dashboard with Widget Customisation}

Rather than a static homepage layout, the dashboard was implemented as a modular Bento-style grid in which users can personalise their view by selecting which widgets to display. Users can choose from widgets including a daily timeline, upcoming deadlines, task list, reading plan, and AI study coach panel. Widget preferences are persisted in the user's settings. This design decision prioritises personalisation: different students have different workflows, and a fixed layout would not serve all use cases equally. The grid structure ensures visual consistency is maintained regardless of which widgets are active.

\subsection{Auto-Scheduler Design}

The auto-scheduler feature generates study events based on a student's module deadlines, daily study time preferences set in settings, and sleep schedule (no events are scheduled during the user's configured sleep hours). Rather than implementing the scheduler as a standalone module with its own event model, a wrapper class was used to reference and manage the generated schedule events. This keeps the scheduler coupled to the existing calendar infrastructure, meaning future changes to calendar functionality automatically apply to scheduled events without requiring parallel updates to a separate module. Schedules are named and managed through a dedicated auto-scheduler page, where students can rename or delete a schedule (which removes all associated events). A replan button on the homepage mini-timeline also triggers the auto-scheduler to update the current schedule based on the latest deadlines and preferences.

\subsection{Static-serving + Backend Server Deployment Paradigm}

We once discussed about the practice of deployment between frontend server + backend server and frontend asset + backend server. It is later we agree on keeping the repository uniform and thus chose the method of single server, static frontend asset serving approach.

\section{External Integrations}
\label{sect:integrations}

The system integrates with four external services.

\textbf{iCalendar (RFC 5545)} format is supported for timetable import. King's College London students can provide their timetable URL, taken from the King's College London timetable website, and the system downloads and parses the \texttt{.ics} file to extract scheduled classes and import them directly into the application's calendar as events.

\textbf{OpenAI API} powers the AI study coach feature. When a student requests insights or asks a question through the coach interface, the system constructs a context object from the student's study session history, streak statistics, peak study hours, dark mode usage patterns, and upcoming calendar events, and sends this to the OpenAI API. The response is returned as personalised, data-aware feedback. The integration is conditionally loaded: if the \texttt{openai} package is not installed or the API key is not configured in the environment, the backend returns an HTTP 503 response and the coach panel renders an inline error message in place of the coach output, leaving all other features of the application entirely unaffected.

\textbf{Mapbox GL} is used to render the campus map feature, which displays the five King's College London campus locations (Strand, Guy's, Waterloo, St Thomas, and Denmark Hill) and provides journey planning functionality. King's College London students can calculate walking routes to any campus using the Mapbox Directions API, or public transport routes using the TfL Journey Planner API, based on their saved home address.

\textbf{Transport for London (TfL) API} is used alongside Mapbox to provide public transport routing on the campus map, giving King's College London students the option to plan their journey to campus by tube, bus, or rail.
