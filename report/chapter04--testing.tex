\chapter{Testing}
\label{chap:testing}

Testing was integrated throughout development to ensure the reliability and correctness of the system. The application consists of a backend implemented using Python and Django, and a frontend implemented using React with Vite. Automated tests were developed for both parts of the system and were complemented by manual testing of the deployed application. The team followed an \textbf{Agile development approach with continuous testing}, meaning tests were written alongside feature development.

\section{Automated Testing}

Backend tests were implemented using Django’s built-in testing framework together with the Python coverage library. These tests validate database models, helper functions, and API endpoints. For example, tests verify behaviour for models such as \textbf{test\_deadline\_model.py}, which checks default values, valid deadline types, and cascading deletion with its parent module, and \textbf{test\_notification\_model.py}, which verifies notification-related model behaviour. API endpoints are also tested in files such as \textbf{test\_auth\_login\_view.py}, which checks successful and unsuccessful login responses, \textbf{test\_task\_detail\_view.py}, which validates task retrieval and update behaviour, and \textbf{test\_society\_view.py}, which covers society-related endpoint behaviour. A representative backend test verifying model behaviour is \textbf{test\_deadline\_model.py}, because it confirms that the model stores required data correctly and applies expected defaults when optional fields are omitted.

Frontend tests were written using \textbf{Vitest}, which integrates with the Vite development environment. These tests validate React components, hooks, context providers, and full page behaviour. Examples include component tests such as \textbf{TaskCard.test.jsx}, which checks interactions such as opening menus, editing tasks, and starting study sessions, \textbf{NotificationToast.test.jsx}, which verifies toast rendering and timed dismissal behaviour, and \textbf{UserSearch.test.jsx}, which validates filtering and result selection. Hook tests such as \textbf{useTimerLogic.test.js} and \textbf{useCalendarEvents.test.js} verify state updates and asynchronous event loading. A representative frontend component test verifying user interaction is \textbf{TaskCard.test.jsx}, because it exercises several user actions and confirms that the interface responds correctly.

The frontend test suite contains \textbf{961 test files across 157 directories}, while the backend suite contains \textbf{100 test files across 22 directories}. Together this results in \textbf{1,061 automated test files}. After implementing each feature, the developer responsible for that feature also wrote the corresponding automated tests, ensuring that new functionality was validated immediately and that each team member contributed automated tests (II.5).

\section{Test Coverage}

Code coverage tools were used to evaluate the completeness of the automated tests. During \textbf{week 6}, the team reviewed the entire test suite and improved it until coverage reached \textbf{100\%}. This ensured that all major components of the system were executed during automated testing and satisfied the coverage requirements in the marking criteria (III.5.1, III.5.2, IV.5.1, IV.5.2).

Tests were designed to cover multiple input partitions, including \textbf{valid inputs, invalid inputs, and edge cases}. For example, tests validate behaviour when requests contain missing fields or invalid authentication tokens. An example input validation test can be found in \textbf{test\_auth\_login\_view.py}, where invalid credentials return \textbf{401 Unauthorized} and empty login data returns \textbf{400 Bad Request}, demonstrating that incorrect inputs are handled separately from valid requests (V.5.1, V.5.2).

\section{Test Code Quality}

Test code quality was maintained through the use of reusable fixtures and mixins to avoid duplicated setup logic. Shared configuration is defined in \textbf{test\_case\_support.py}, which provides reusable base classes, authenticated API client setup, and helper assertions for event-related tests. Additionally, a script was used to detect duplicated code across the repository, ensuring repeated test implementations were refactored or removed (V.3.6).

Another script checked the structure of test functions to ensure they remained short and readable. Tests were typically limited to \textbf{fewer than 25 lines} and avoided deep control-flow nesting. A concise unit test verifying a single behaviour can be found in \textbf{test\_seed\_homepage\_widgets.py}, where one short test confirms that only the expected core homepage widgets are selected during seeding. Tests also follow clear naming conventions such as \textbf{TaskCard.test.jsx} and \textbf{test\_task\_detail\_view.py} (V.3.5, V.3.7).

\section{Manual Testing}

Manual testing was performed during \textbf{weekly team meetings}. The team tested both the development and deployed versions of the system by performing common user workflows such as creating tasks, navigating the calendar, and interacting with social features.

Manual testing was primarily used to verify \textbf{user interface behaviour and usability}, which are difficult to fully validate using automated tests. A detailed list of manual tests, including actions and expected results, is provided in \textbf{Appendix A}. This process also ensured the deployed application was regularly validated (III.4.2).

\section{Limits of Testing}

Automated testing provides advantages such as \textbf{speed, repeatability, and regression detection}. However, automated tests cannot easily detect issues related to layout or overall user experience. Manual testing helps identify such issues but cannot be executed as consistently as automated tests.

\section{Threats to Validity}

Although the project includes \textbf{1,061 automated test files} and achieves \textbf{100\% code coverage}, this does not guarantee that the system is completely free of defects. Code coverage indicates that code was executed during testing, but it does not ensure that every possible logical error or edge case has been detected.

Some tests also rely on simulated inputs rather than real-world conditions. For example, \textbf{test\_email\_utils.py} validates behaviour using mocked email-sending and template-rendering functions rather than a real mail server, which makes the test reliable and isolated but less representative of full production behaviour.

Despite these limitations, the combination of extensive automated testing, full coverage analysis, and regular manual testing provides strong confidence in the reliability of the system.
